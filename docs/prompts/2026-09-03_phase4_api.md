## Deliverable — `src/docvalidator/api/`

`main.py` with a FastAPI app:

- `GET /health` → `{"status": "ok"}` (liveness, no dependencies)
- `POST /v1/validate` — accepts BOTH:
  - multipart/form-data: `file: UploadFile` (PDF or .txt) + `config: str` (JSON string of ValidationConfig)
  - application/json: `{"content_b64": str | "text": str, "filename": str | null, "config": ValidationConfig}`
    (at least one of content_b64/text; reject with 422 if both or neither)
- `POST /v1/extract` — same input contract, returns the DocumentExtraction only
- Extraction backend selection: request-level `"extraction_backend": "offline" | "llm"` in the JSON body
  (default from env `VALIDATOR_EXTRACTION_BACKEND`, itself default "offline"). For this phase, "llm"
  may raise HTTP 501 with a clear message if no LLM adapter exists yet — the adapter lands in phase 7.
- Errors: unreadable PDF / bad config → HTTP 422 with structured error body; unexpected internal
  error → HTTP 500 with request_id, no stack trace leak.

`logging_setup.py`: structured JSON logging to stdout — one line per request:
`{"ts", "level", "request_id", "route", "method", "status_code", "latency_ms", "backend", "verdict_status"}`.
request_id: incoming `X-Request-ID` header or generated uuid4; always echoed back in the response header.
Use a FastAPI middleware; keep it simple (json.dumps of a dict, no structlog dependency).

Response model for /v1/validate: the `Verdict` Pydantic model from domain (nested extraction
included) + top-level `request_id`.

## Tests (`tests/integration/`)

Use `fastapi.testclient.TestClient` (no running server needed):
- health returns 200
- validate via JSON with text content of a good fixture → PASS verdict, schema shape correct
- validate via multipart with a .txt fixture → same result
- invalid config (max_age_days=0) → 422

- X-Request-ID echoed; when absent, response has a generated request_id
